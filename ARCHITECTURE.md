# ARCHITECTURE

## Обзор

`12 недель` — персональный планировщик одного или нескольких 12-недельных циклов.
Главный экран показывает верхнеуровневые цели на диаграмме Ганта, а страница
недели раскрывает конкретный план: обычные чек-листы, цели с подзадачами и
повторяемые действия по дням недели.

Приложение строится на Next.js App Router и Supabase:

- Next.js отвечает за страницы, серверную композицию и HTTP API;
- Supabase Auth — за вход и пользовательскую сессию;
- Supabase Postgres — за циклы, недели, цели и отметки выполнения;
- Row Level Security (RLS) изолирует данные пользователей;
- StageShow — единственная дизайн-система, источник компонентов, графики, тем и
  визуальных токенов;
- Supabase Realtime, Storage и фоновые задачи не нужны для MVP.

Текущая реализация хранит настройки, цели и выполнение в Supabase. Доступ
защищён Supabase Auth с регистрацией и входом по email и паролю; демоданные и
локальное постоянное хранилище приложению не нужны.

## Границы продукта

### Входит в MVP

- регистрация, вход и выход;
- создание 12-недельного цикла с датой начала;
- диаграмма Ганта по 12 неделям;
- создание, редактирование, сортировка и архивирование целей;
- переход из недели Ганта на подробную страницу недели;
- три варианта недельной цели:
  - обычная цель с чек-листом;
  - повторяемая цель с выбранными днями недели;
  - цель с вложенными пунктами и подпунктами;
- отметка выполнения пунктов и повторений;
- прогресс недели, цели и всего цикла;
- темы StageShow `light`, `dark`, `blueprint` и `glass`, переключаемые без замены
  компонентов и локальных визуальных исключений.

### Не входит в MVP

- команды, роли, приглашения и совместный доступ;
- комментарии и история обсуждений;
- файлы, изображения, S3 и Supabase Storage;
- Telegram, email-уведомления и push-уведомления;
- подписки, платежи и административная панель;
- MCP/OAuth-интеграция;
- сложная аналитика, AI-функции и внешние календари;
- offline-first синхронизация и разрешение конфликтов.

Эти возможности не закладываются заранее в таблицы и API. Их следует добавлять
только после появления подтверждённого пользовательского сценария.

## Технологический стек

### Уже используется

- `next@16` с App Router;
- `react@19`;
- TypeScript в строгом режиме;
- CSS в `src/app/globals.css`;
- локальная копия StageShow в `stageshow-preview`, которая становится основой
  обязательной дизайн-системы приложения.

### Добавляется для Supabase

- `@supabase/ssr` — cookie-based сессия в Next.js;
- `@supabase/supabase-js` — типизированный клиент Auth/Postgres;
- `zod` — единая валидация входных данных Route Handlers;
- `lucide-react` — зависимость StageShow для графики; напрямую в продуктовых
  компонентах не используется;
- сгенерированные Supabase-типы — `src/types/database.ts`.

React Query на старте не обязателен: страницы можно загружать как Server
Components, а после mutations вызывать `revalidatePath`. Его стоит добавить,
если появятся сложные optimistic updates, частые фоновые обновления или заметный
клиентский кэш.

## Архитектурные принципы

1. **Supabase — источник истины.** Тема, дата первой недели, цели и прогресс
   хранятся в Postgres; `localStorage` не используется.
2. **RLS — обязательная граница доступа.** Серверные проверки улучшают сообщения
   об ошибках, но не заменяют политики базы данных.
3. **Цель цикла и план недели — разные сущности.** Цель формирует полосу Ганта,
   недельный план содержит исполнимые карточки и отметки.
4. **RLS защищает прямой Data API.** Текущий однопользовательский MVP читает и
   пишет через браузерный Supabase-клиент с JWT вошедшего пользователя.
5. **Серверный слой добавляется по мере усложнения операций.** Для транзакций,
   нескольких циклов и постоянных аккаунтов используются Route Handlers/RPC.
6. **Производные значения не дублируются без необходимости.** Проценты прогресса
   вычисляются из пунктов и выполнений, а не хранятся отдельными полями.
7. **MVP остаётся монолитом.** Отдельные сервисы, очереди и микросервисы здесь не
   дают пользы.
8. **StageShow — единственный UI-kit.** Нельзя создавать собственный аналог уже
   существующего компонента, использовать браузерный вид по умолчанию или
   подключать вторую библиотеку компонентов.
9. **Отсутствующий компонент — продуктовый вопрос.** Если подходящего компонента
   StageShow нет, реализация останавливается и у пользователя запрашивается одно
   из решений: расширить StageShow, изменить сценарий или явно разрешить
   исключение. Разработчик не выбирает это самостоятельно.
10. **Проверки запускаются только по команде пользователя.** Нельзя самостоятельно
    запускать build, lint, typecheck, тесты, e2e, Supabase-проверки, StageShow
    rehearsal/film gate или другие автоматические проверки. Изменения готовятся
    без их запуска, пока пользователь явно не попросит проверить проект.

## Слои и ответственность

`page.tsx` и `layout.tsx` получают параметры маршрута, загружают данные и
компонуют крупные блоки. В них не размещается SQL-подобная логика и сложные
правила изменения данных.

Рекомендуемая структура:

```text
src/app/

  (app)/
    layout.tsx
    page.tsx
    cycles/new/page.tsx
    cycles/[cycleId]/page.tsx

    settings/page.tsx
  api/
    cycles/route.ts
    cycles/[cycleId]/route.ts
    cycles/[cycleId]/goals/route.ts
    goals/[goalId]/route.ts
    goals/[goalId]/reorder/route.ts
    weeks/[weekId]/route.ts
    weeks/[weekId]/plans/route.ts
    plans/[planId]/route.ts
    checklist-items/[itemId]/route.ts
    occurrences/[occurrenceId]/route.ts
```

### 2. Фича-модули: `src/modules`

UI и клиентская логика группируются по пользовательским сценариям, а не по типам
файлов:

```text
src/modules/
  auth/
  cycles/
  gantt/
  goals/
  week/
  settings/
```

Типичный модуль:

```text
src/modules/goals/
  components/
    GoalCard.tsx
    GoalForm.tsx
    GoalTypePicker.tsx
  api/
    createGoal.ts
    updateGoal.ts
  schemas.ts
  types.ts
```

Компоненты текущего прототипа (`TrackerApp`, `GoalCard`, `GoalModal`) следует
переносить в модули постепенно. Одномоментная перестройка каталогов не нужна.

### 3. Общие компоненты и утилиты

```text
src/shared/
  stageshow/       # неизменённая копия StageShow kit и его CSS
  ui/              # только продуктовые композиции из StageShow, не новый kit
  lib/            # чистые функции дат, прогресса и форматирования
  types/          # общие прикладные типы

src/lib/
  supabase/
    client.ts      # browser client
    server.ts      # cookie-aware server client
    middleware.ts  # обновление auth-сессии
  auth/

  api/
    errors.ts
    parseRequest.ts
```

`service_role` не используется в пользовательских запросах и никогда не попадает
в браузер. Для обычной работы достаточно Supabase-клиента с JWT пользователя и
RLS.

### 4. Дизайн-система StageShow

StageShow копируется в приложение как локальный kit согласно его инструкции и
подключается через один публичный entrypoint. Продуктовый код не импортирует
внутренние файлы StageShow и не копирует их реализацию в свои модули.

Базовый путь после интеграции:

```text
src/shared/stageshow/
  kit/
    index.ts
    stageshow.css
    ...
  product-look.css
  index.ts
```

Разрешённые строительные блоки берутся из StageShow:

- каркас и поверхности: `Stage`, `Window`, `Card`, `Divider`;
- списки и контент: `Row`, `Text`, `Bar`;
- формы и управление: `Field`, `Button`, `Segmented`, `Toggle`, `Tabs`, `Chip`;
- статусы и обратная связь: `Badge`, `Meter`, `Spinner`, `Toast`, `Tooltip`;
- графика: `Icon`, `BrandMark`, `Chart`, `Connector`;
- раскрывающиеся поверхности и движение: `Menu`, `Popover`, `Collapse`, `Swap`,
  `Scroll`, `States`.

Этот список не является разрешением имитировать отсутствующий компонент из
нескольких `div`. Композиция допустима только для предметной области: например,
карточка цели может собираться из `Card`, `Row`, `Badge` и `Meter`. Новый базовый
контрол, повторяющий `Dialog`, `Select` или `Checkbox`, продуктовый модуль создавать
не может.

#### Обязательные правила UI

1. Перед разработкой экрана проверяется экспорт `kit/index.ts` и каталог
   StageShow. Сначала выбирается существующий компонент, затем проектируется
   композиция.
2. `button`, `input`, `select`, `textarea`, браузерный `dialog` и другие нативные
   контролы нельзя выводить пользователю напрямую. Их разрешено использовать
   только внутри реализации StageShow.
3. Нельзя создавать локальные `Button`, `Card`, `Select`, `Modal`, `Checkbox`,
   `Tabs`, `Toast`, `Badge`, `Icon` и похожие примитивы, даже если реализация
   кажется простой.
4. Нельзя подключать Ant Design, MUI, Radix, shadcn/ui, Headless UI или другой
   параллельный UI-kit без отдельного решения пользователя.
5. Иконки используются только через StageShow `Icon`/`BrandMark`. Запрещены emoji,
   произвольные SVG, текстовые символы вместо иконок и прямой импорт
   `lucide-react` из продуктового кода.
6. Геометрия StageShow-компонента не переопределяется внешними CSS-селекторами.
   Для настройки используются его props и токены. `!important` запрещён.
7. Собственные CSS-классы допустимы только для раскладки предметных композиций,
   адаптивности и значений, которых нет в StageShow API. Они не должны рисовать
   новый контрол или дублировать визуальное состояние существующего компонента.
8. Все интерактивные состояния — focus, hover, pressed, selected, disabled,
   loading, success и error — должны быть состояниями StageShow-компонента, а не
   отдельной самодельной разметкой.
9. Доступность не ухудшается ради внешнего вида: используются семантика и
   клавиатурное поведение, уже заложенные в компонент; недостающая accessibility
   считается отсутствующим компонентом, а не поводом сделать обходной вариант.

#### Темы и токены

`Stage`/StageShow look — единственный источник визуальных значений. Приложение
поддерживает встроенные темы `light`, `dark`, `blueprint`, `glass`; palette и
fidelity выбираются централизованно. Все компоненты читают одну систему токенов:

- цвет: canvas, surface, raised, line, ink, accent и status tones;
- типографика: единый font stack и текстовая шкала;
- форма: `--ss-radius-sm`, `--ss-radius-md`, `--ss-radius-lg`,
  `--ss-radius-window`, `--ss-radius-pill`;
- плотность: `--ss-control`, `--ss-row`;
- глубина: системные StageShow shadows и surface steps.

Брендовый вид задаётся один раз в `product-look.css` поверх токенов StageShow и
обязан иметь варианты для всех поддерживаемых тем. В feature CSS запрещены
жёстко заданные hex-цвета, собственные radius/shadow/font-family и отдельные
«починки» тёмной темы. Выбранная тема хранится локально и применяется до
гидрации, чтобы не было вспышки другой темы.

Добавление или изменение темы принимается только вместе с визуальной проверкой
всех StageShow-примитивов и ключевых экранов. Экран считается готовым, если он
сохраняет иерархию, контраст и состояния во всех четырёх темах.

#### Реестр расширений StageShow

Перед реализацией экранов была сверена локальная версия StageShow. Пользователь
явно разрешил расширить сам kit недостающими базовыми компонентами. В StageShow
добавлены и экспортированы:

- `Dialog` для большого окна добавления цели;
- `Select` для категории, темы, времени и количества повторений;
- интерактивный `Checkbox` с обычным и дневным tile-вариантом;
- универсальный `Gantt` для недельной timeline/grid-композиции.

Все четыре компонента живут в `src/shared/stageshow/kit/controls`, используют
только StageShow-токены и доступны продукту через общий `kit/index.ts`.

Отдельные `DatePicker` и `TimePicker` пока не создавались: текущему прототипу
достаточно выбора заранее заданного времени через StageShow `Select`, а дата
выводится из выбранной недели. Если позже понадобится произвольный ввод даты или
времени, снова требуется явный выбор пользователя:

1. расширить StageShow новым базовым компонентом;
2. перестроить сценарий из уже существующих компонентов StageShow;
3. разрешить конкретное документированное исключение.

Решение записывается в этот раздел до написания нового базового компонента. Пока
решения нет, соответствующий сценарий считается заблокированным, а не частично
реализованным.

#### Проверка гармоничности

- каждый новый экран проверяется в `light`, `dark`, `blueprint`, `glass`;
- рядом не должно быть компонентов разной плотности, радиусов или визуального
  языка;
- активная цель и прогресс остаются главным фокусом, декоративная графика не
  конкурирует с данными;
- для маркетинговых скриншотов и демонстраций используются framing, motion и
  rehearsal-процесс StageShow, а не отдельная стилизация продукта;
- изменение токена проверяется на Ганте, странице недели, формах и toast-состоянии.

### 5. API-слой: `src/app/api/**/route.ts`

Route Handler выполняет один и тот же порядок действий:

1. получает проверенного пользователя через `requireUser`;
2. валидирует `params`, query и JSON-тело схемой Zod;
3. выполняет бизнес-операцию через `src/server/services`;
4. обращается к Supabase пользовательским клиентом;
5. возвращает единообразный JSON и корректный HTTP-статус;
6. инвалидирует затронутые страницы через `revalidatePath`.

Бизнес-операции, затрагивающие несколько таблиц, выполняются одной Postgres RPC
функцией или транзакцией в БД. Например, создание цикла одновременно создаёт 12
строк `weeks`, а создание повторяемого плана — правило и его события на неделю.

Рекомендуемый формат ошибки:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте заполненные поля",
    "fields": { "title": "Название обязательно" }
  }
}
```

## Пользовательские маршруты

- `/` без сессии — экран входа, регистрации и восстановления пароля;
- `/` — редирект в активный цикл или экран создания первого цикла;
- `/cycles/new` — создание цикла;
- `/cycles/[cycleId]` — основной экран с Гантом и сводкой;
- `/cycles/[cycleId]/weeks/[weekNumber]` — подробная страница недели;
- `/settings` — профиль, часовой пояс и тема.

Модальное добавление цели может открываться поверх экрана цикла или недели. URL
для него не обязателен, пока не нужна прямая ссылка или восстановление модалки
после перезагрузки.

## Модель данных Supabase

Текущий MVP реализован минимальной схемой из `settings`, `goals`, `goal_items` и
`goal_occurrences`. `settings` содержит `first_week_date`, `theme` и `timezone`;
номер недели хранится у цели, а конкретные даты вычисляются от первой недели.
Полная воспроизводимая схема, ограничения и RLS находятся в
`supabase/migrations/20261108000000_initial_tracker_schema.sql`.

Описанная ниже расширенная модель с `cycles` и `weeks` остаётся направлением для
версии с историей нескольких циклов и не создаётся текущей миграцией.

Все идентификаторы — `uuid`, даты хранятся как `date`, моменты времени — как
`timestamptz`. Во всех изменяемых таблицах есть `created_at` и `updated_at`.

### `profiles`

Минимальное расширение `auth.users`:

- `id uuid primary key references auth.users(id) on delete cascade`;
- `display_name text`;
- `timezone text not null default 'Europe/Moscow'`.

Триггер создаёт профиль после регистрации. Email остаётся в `auth.users` и не
дублируется.

### `cycles`

- `id uuid primary key`;
- `user_id uuid not null references auth.users(id) on delete cascade`;
- `title text not null`;
- `start_date date not null` — понедельник первой недели;
- `status text not null` — `draft | active | completed | archived`;
- `created_at`, `updated_at`.

Ограничения:

- дата начала нормализуется до понедельника;
- у пользователя не больше одного активного цикла;
- номер текущей недели вычисляется по `start_date`, а не хранится в `cycles`.

### `weeks`

- `id uuid primary key`;
- `cycle_id uuid not null references cycles(id) on delete cascade`;
- `number smallint not null check (number between 1 and 12)`;
- `start_date date not null`;
- `end_date date not null`;
- `focus text`;
- `reflection text`;
- `created_at`, `updated_at`;
- `unique (cycle_id, number)`.

12 недель создаются вместе с циклом. Это упрощает маршруты, недельные планы и
проверку принадлежности данных.

### `goals`

Верхнеуровневая цель и полоса на Ганте:

- `id uuid primary key`;
- `cycle_id uuid not null references cycles(id) on delete cascade`;
- `title text not null`;
- `description text`;
- `category text`;
- `color text not null`;
- `kind text not null` — `checklist | recurring | structured`;
- `start_week smallint not null`;
- `end_week smallint not null`;
- `target_value numeric`;
- `target_unit text`;
- `sort_order integer not null`;
- `status text not null` — `active | completed | archived`;
- `created_at`, `updated_at`.

Проверки: недели находятся в диапазоне 1–12, `start_week <= end_week`, цвет имеет
допустимый формат. Для однонедельной цели начало и конец совпадают.

### `weekly_plans`

Связь цели с конкретной неделей и основа карточки подробной страницы:

- `id uuid primary key`;
- `goal_id uuid not null references goals(id) on delete cascade`;
- `week_id uuid not null references weeks(id) on delete cascade`;
- `title_override text`;
- `notes text`;
- `target_value numeric`;
- `sort_order integer not null`;
- `created_at`, `updated_at`;
- `unique (goal_id, week_id)`.

При создании или изменении диапазона цели сервис синхронизирует недельные планы:
добавляет недостающие и удаляет только пустые планы. Если в исключаемой неделе уже
есть выполнения, API требует отдельного подтверждения.

### `checklist_items`

Пункты обычных и структурированных целей:

- `id uuid primary key`;
- `plan_id uuid not null references weekly_plans(id) on delete cascade`;
- `parent_id uuid references checklist_items(id) on delete cascade`;
- `title text not null`;
- `is_completed boolean not null default false`;
- `completed_at timestamptz`;
- `sort_order integer not null`;
- `created_at`, `updated_at`.

Для `checklist` поле `parent_id` всегда `null`. Для `structured` допускается один
уровень вложенности в MVP; это ограничивается сервисом, чтобы UI и прогресс были
предсказуемыми.

### `recurrence_rules`

- `id uuid primary key`;
- `plan_id uuid not null unique references weekly_plans(id) on delete cascade`;
- `weekdays smallint[] not null` — ISO-дни `1..7`;
- `time_of_day time`;
- `target_count smallint not null`;
- `created_at`, `updated_at`.

### `recurrence_occurrences`

Конкретные отметки повторяемой цели:

- `id uuid primary key`;
- `rule_id uuid not null references recurrence_rules(id) on delete cascade`;
- `scheduled_date date not null`;
- `is_completed boolean not null default false`;
- `completed_at timestamptz`;
- `created_at`, `updated_at`;
- `unique (rule_id, scheduled_date)`.

События создаются при сохранении правила только для соответствующей недели.
Отдельный cron для этого не требуется.

## Связи данных

```text
auth.users
  └── profiles
  └── cycles
        ├── weeks
        └── goals
              └── weekly_plans ── weeks
                    ├── checklist_items ── checklist_items (parent)
                    └── recurrence_rules
                          └── recurrence_occurrences
```

## Прогресс

- обычная цель: выполненные корневые пункты / все корневые пункты;
- цель с подзадачами: выполненные конечные пункты / все конечные пункты;
- повторяемая цель: выполненные события / `target_count`;
- неделя: среднее прогресса непустых недельных планов;
- цель цикла: среднее прогресса её недельных планов;
- цикл: среднее прогресса активных целей.

Пустой план возвращает `0%`, а не деление на ноль. На первом этапе вычисления
выполняются серверными функциями TypeScript. При появлении больших объёмов их
можно перенести в SQL view без изменения UI-контрактов.

## Основные API-группы

### Циклы

- `GET /api/cycles` — циклы текущего пользователя;
- `POST /api/cycles` — создать цикл и 12 недель;
- `GET /api/cycles/[cycleId]` — цикл, цели и данные Ганта;
- `PATCH /api/cycles/[cycleId]` — название, дата начала, статус;
- `DELETE /api/cycles/[cycleId]` — удалить цикл после явного подтверждения.

### Цели и Гант

- `POST /api/cycles/[cycleId]/goals` — создать цель и недельные планы;
- `PATCH /api/goals/[goalId]` — изменить поля или диапазон недель;
- `DELETE /api/goals/[goalId]` — архивировать по умолчанию;
- `PATCH /api/goals/[goalId]/reorder` — изменить порядок строк Ганта.

### Неделя

- `GET /api/weeks/[weekId]` — неделя со всеми карточками и прогрессом;
- `PATCH /api/weeks/[weekId]` — фокус и рефлексия;
- `POST /api/weeks/[weekId]/plans` — добавить цель непосредственно в неделю;
- `PATCH /api/plans/[planId]` — настройки карточки недели;
- `DELETE /api/plans/[planId]` — удалить карточку из недели.

### Выполнение

- `POST /api/plans/[planId]/items` — добавить пункт;
- `PATCH /api/checklist-items/[itemId]` — текст, порядок, состояние;
- `DELETE /api/checklist-items/[itemId]` — удалить пункт;
- `PATCH /api/occurrences/[occurrenceId]` — отметить повторение выполненным.

Для переключения checkbox сервер принимает желаемое состояние, а не команду
`toggle`. Повторный одинаковый запрос поэтому идемпотентен.

## Авторизация и RLS

Источник пользователя — Supabase Auth cookie. Сервер получает пользователя через
`supabase.auth.getUser()`, а не доверяет данным из формы или `user_id` из URL.

Политики строятся по цепочке владения:

- `cycles.user_id = auth.uid()`;
- `weeks` доступны, если принадлежащий цикл принадлежит `auth.uid()`;
- `goals` доступны через их цикл;
- `weekly_plans` доступны через цель и неделю того же цикла;
- пункты, правила и события доступны через `weekly_plans`.

Для каждой таблицы включается RLS и создаются отдельные `select`, `insert`,
`update`, `delete` policies. Внешние ключи и RLS дополняют друг друга: FK
сохраняют целостность, RLS ограничивает пользователя.

В MVP нет ролей внутри приложения: каждый пользователь видит и меняет только свои
данные. Это намеренно проще проектного примера с участниками и приглашениями.

## Потоки данных

### Открытие диаграммы Ганта

1. Server Component получает cookie-сессию.
2. Загружает цикл, его 12 недель и активные цели.
3. Сервер преобразует данные в компактный `GanttViewModel`.
4. Клиентский компонент отвечает только за выделение недели, drag-and-drop и
   открытие модалок.

### Создание цели

1. Форма выбирает тип цели и валидирует обязательные поля на клиенте.
2. `POST /api/cycles/[cycleId]/goals` повторно валидирует payload.
3. Сервис создаёт `goals`, нужные `weekly_plans` и дочерние записи атомарно.
4. API возвращает созданную цель и вызывает `revalidatePath` экрана цикла.
5. UI закрывает модалку и показывает подтверждение.

### Отметка пункта

1. UI оптимистично меняет checkbox.
2. `PATCH` передаёт явное `is_completed`.
3. API проверяет владение через пользовательский Supabase-клиент и RLS.
4. При ошибке UI возвращает прежнее состояние и показывает сообщение.
5. Прогресс пересчитывается из актуальных пунктов.

### Изменение дней повторения

1. Пользователь сохраняет новый набор дней.
2. Одна транзакционная операция обновляет `recurrence_rules`.
3. Невыполненные события недели синхронизируются с новым расписанием.
4. Уже выполненные события сохраняются, чтобы не терять историю.

## SQL и миграции

Рекомендуемая структура:

```text
supabase/
  migrations/
    0001_profiles.sql
    0002_cycles_and_weeks.sql
    0003_goals_and_plans.sql
    0004_checklists_and_recurrence.sql
    0005_rls.sql
    0006_functions.sql
  seed.sql
```

Миграции применяются последовательно через Supabase CLI. Ручные изменения схемы
в production через Dashboard после запуска проекта не допускаются: каждое
изменение должно быть воспроизводимо из репозитория.

Полезные RPC-функции MVP:

- `create_cycle_with_weeks(...)`;
- `create_goal_with_plans(...)`;
- `update_goal_week_range(...)`;
- `upsert_recurrence_rule_with_occurrences(...)`.

## Валидация и ограничения

- заголовки: 1–120 символов;
- описание/заметка: до 2 000 символов;
- одна цель не выходит за пределы 12 недель;
- повторение содержит хотя бы один уникальный день `1..7`;
- `target_count` не превышает число выбранных дней;
- дочерний пункт принадлежит тому же плану, что и родитель;
- архивная цель не принимается в расчёт текущего прогресса;
- дата события повторения должна попадать в диапазон его недели.

Критичные ограничения дублируются в Postgres `check`/FK/unique constraints, даже
если они уже проверяются Zod-схемой.

## Ошибки, логирование и наблюдаемость

- пользователю показываются короткие сообщения без SQL и stack trace;
- сервер логирует код операции, route, `user_id`, id сущности и безопасное
  описание ошибки;
- access token, cookie, содержимое заметок и персональные данные не логируются;
- ожидаемые ошибки имеют стабильные коды: `UNAUTHORIZED`, `NOT_FOUND`,
  `VALIDATION_ERROR`, `CONFLICT`, `INTERNAL_ERROR`;
- на MVP достаточно платформенных логов Vercel и Supabase.

## Тестирование

Ни одна команда из этого раздела не запускается автоматически после изменений.
Проверки выполняются только после явной команды пользователя. Рекомендуемый набор
перед production, когда пользователь разрешит его запуск:

- unit-тесты чистых функций дат и прогресса;
- unit-тесты Zod-схем для трёх типов целей;
- интеграционные тесты RPC-функций и RLS для двух разных пользователей;
- e2e-сценарии: создать цикл, добавить каждый тип цели, открыть неделю, отметить
  пункт, изменить расписание повторения, убедиться в прогрессе;
- `npm run lint` и `npm run build` в CI.

Особенно важно тестировать границы: неделя 1/12, цикл через Новый год, смена
часового пояса, пустые цели и попытка доступа к чужому UUID.

## Этапы перехода с текущего прототипа

1. Добавить Supabase-клиенты, Auth middleware и страницы входа.
2. Создать SQL-миграции, RLS и типы базы.
3. Перенести `Goal` из `src/types/tracker.ts` в новую доменную модель.
4. Заменить чтение `localStorage` загрузкой настроек и целей из Supabase.
5. Вынести создание/редактирование целей в Route Handlers.
6. Добавить `weekly_plans`, чек-листы и повторения.
7. Разделить текущий `TrackerApp` на модули Ганта и страницы недели.
8. Скопировать StageShow kit в `src/shared/stageshow`, подключить
   `product-look.css` и заменить текущие самодельные контролы доступными
   StageShow-компонентами.
9. Использовать согласованные расширения StageShow: `Dialog`, `Select`,
   `Checkbox`, `Gantt`; не создавать их продуктовые аналоги.
10. Проверить каждый экран во всех четырёх темах StageShow.
11. Хранить тему и дату первой недели в `settings`, не используя `localStorage`.

## Что взято из архитектуры `andzor`

Сохранены и адаптированы:

- Next.js App Router как верхний слой маршрутов и layout-композиции;
- Route Handlers как backend-for-frontend;
- Supabase Auth + Postgres и пользовательский JWT-клиент;
- RLS как обязательная защита данных;
- деление на `src/app`, фича-модули, shared-компоненты и `src/lib`;
- клиентские API-обёртки рядом с соответствующей фичей;
- отдельные SQL-миграции и политики RLS в репозитории;
- последовательный поток `UI -> API -> Supabase`;
- правило выносить переиспользуемые типы и утилиты из компонентов;
- стандартные команды локальной разработки и production build.

Дополнительно зафиксировано отдельное требование текущего продукта: StageShow —
единственный источник UI-компонентов, графики, стилей и тем. Это правило не было
взято из `andzor` и имеет приоритет над его UI-стеком.

Упрощены или исключены как лишние для этого продукта:

- проекты, участники, роли и приглашения;
- отдельные справочники заказчиков, подрядчиков и сотрудников;
- S3, галерея, документы и обработка изображений;
- Telegram, SMTP, уведомления и cron;
- MCP, OAuth-шлюз и приватная MCP-схема;
- платежи, подписки и service-role операции;
- BlockNote, TipTap, Ant Design, Radix и сторонние drag-and-drop/UI-библиотеки как
  обязательная часть стека; визуальный слой полностью заменён StageShow;
- dashboard с корпоративными KPI;
- интернационализация через `next-intl`: для MVP интерфейс русскоязычный, но
  пользовательский текст не должен смешиваться с ключами БД;
- интерфейсы пропсов с обязательным префиксом `I`: используются обычные
  описательные `type`/`interface` по принятому стилю текущего проекта.

Главное отличие — архитектура организована вокруг одного владельца, 12-недельного
цикла и трёх типов целей. Корпоративные сущности из примера не переносятся «на
будущее», поэтому схема и API остаются небольшими и проверяемыми.
